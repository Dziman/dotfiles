# Test writing strategy

- **One scenario per test.** Multiple inputs → separate tests or a parameterized test, never chained scenarios in one method.
- Tests **mirror the subject's location** and use a predictable name (`<Subject>Test` / `test_<subject>`). The failure message should name the broken case unambiguously.
- **Name each case by the business rule, not the variable values.** The condition part of a test name says *why* the case matters in domain terms, not the mechanical state of an input. A branch guarding a missing name → `missingName` / `productWithoutName` (whichever fits the context), never `nameIsNull` / `nullName`. A reader should learn the rule under test from the name alone, and the name should survive a refactor of *how* the rule is implemented (the field becoming an `Optional`, the check moving) — a name tied to `null` rots the moment the mechanics change.
- **Reuse fixtures/builders** before writing new ones; shared fixtures live in the shared test module, not copied per package.
- Test **behavior, not implementation**; cover boundaries and error paths, not just the happy path.
- **A unit test covers logic, never volume or speed.** Build the *smallest* input that can express the rule: if a rule holds for three records it does not hold harder for three thousand, and the large version only buys wall clock. Never assert on a duration, a row count, a memory figure, or any other measure of cost — those belong to a benchmark or a load test, which is a separate tier with its own budget and its own schedule, not to a suite that runs on every change. When a large fixture exists for its own sake (a performance profile, a scale demo), unit tests assert against a small one and that fixture keeps its own dedicated suite.
- **Assert against data where the rule lives in data.** A rule about what a configuration, script or manifest *declares* is a property of that value — read it directly instead of building the world it describes and observing the result. Reserve the built-world test for the rule that only the building can show, and say in a comment which half each test owns.
- **Red means an assertion failed.** A test that does not compile, or crashes before its assertion runs, is not red — it proves nothing about the behavior. A bug-reproducing test must build against the current code, because the bug lives in code that already exists; if it needs a new symbol, it is not a reproduction yet. For new functionality, first add a stub that compiles and returns a realistic default value, then watch the assertions fail. That default may let some new tests pass, but never all of them — if every one passes, the tests do not exercise the new behavior. Quote the assertion failure message before writing the fix or the implementation.
- Prefer a shared setup helper over hand-stacked boilerplate; keep tests free of logic.
- **Group related tests.** Once **5+** tests target the same method or a common scenario family, group them: at minimum keep them **contiguous and ordered** in the file, but prefer the language's **native grouping construct** (a nested test class, a `describe` block). A group reads as a unit and can share its own setup. Below the threshold, ordering alone is enough.
